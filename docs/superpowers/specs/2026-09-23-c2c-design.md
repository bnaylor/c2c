# c2c — cross-host Claude session coordination: design

Status: approved design, pre-implementation. 2026-09-23.
Companion: `docs/protocol.md` (verified peer-messaging protocol this builds on).

## Problem

Two (eventually N) laptops each run Claude Code sessions on shared,
open-source projects. Coordination between them — PR review handoffs, "run the
suite on your box", issue ownership — is ferried by hand. Claude Code's native
peer messaging (discovery + `SendMessage`) works only between sessions on the
SAME host. c2c extends it across hosts.

Constraints established during brainstorming:
- **Single trust domain.** Only the user's own machines. No teammates in v1.
- **Async is primary, live is a bonus.** Recipients are usually offline when a
  message is sent; delivery must be durable store-and-forward, with immediate
  relay when both ends are up.
- **Agent acts autonomously; human sees it after the fact.** Delivery is not
  approval-gated. All sessions run in auto permission mode.
- **Auto-bridge on git-remote match.** No per-repo opt-in; a project shared by
  2+ hosts is bridged automatically. Project id = git remote URL.
- **Address per project**, with a host qualifier for N>2 and for reply routing.

## What this is NOT

- Not A2A. Not an MCP server. Not Remote Control (different accounts; work runs
  models on Vertex AI, not Anthropic hosting — irrelevant to this channel,
  which is out-of-band from the model API).
- Not a duplicate of GitHub. PR review *requests* and issue *state* live on
  GitHub. c2c carries the out-of-band coordination GitHub can't express —
  notably host-level routing ("the WORK box owns this", which GitHub can't say
  because both hosts are the same GitHub user).

## Foundation: the peer protocol (verified)

Full detail in `docs/protocol.md`. Load-bearing facts, all confirmed by live
capture via `tap.py`:

- Discovery: `~/.claude/sessions/<pid>.json` registry entries.
- Auth: `~/.claude/sessions/<pid>.<sha256(socketPath)>.key` (0600). Hash uses
  the socket path AS WRITTEN — no realpath.
- Transport: `/tmp/cc-socks/<pid>.sock`, NDJSON, 1 MiB line cap, auth line then
  payload line, client speaks first, no sync ack.
- Reverse channel: receiver connects back to the sender's `from` socket,
  authing with the sender's peerToken (found via the no-realpath hash).
- `hop-chain`: opaque per-process HMAC tokens, appended per hop, capped 32.
  Silent drop at chain length > 28 (`hop-runaway`) or own-token ≥ 10 times
  (`hop-loop`). Rate limiter: bucket 30, ~0.5/s refill, 30s dedup.
- Inbound is delivered (not held) in auto mode.

### Spike result — autonomous delivery confirmed (2026-09-23)

A parked `bg` session (`state: blocked`, "awaiting further instructions"),
idle and untouched, received a peer message via `tap.py` and within ~5s:
woke, took a turn, executed the instruction (replied with the exact requested
nonce via SendMessage), logged it to `jobs/<id>/timeline.jsonl`, and re-parked
still-alive. This validates the core premise: a bg session in auto mode is a
durable autonomous worker that wakes on delivery, acts, reports, and stays
ready. It is the preferred delivery target.

## Architecture

Three parts; names avoid Claude Code's own `bridgeSessionId`:

- **ferry** — per-host daemon (grown from `tap.py`).
- **hub** — one public store-and-forward server.
- **sessions** — unchanged; no plugin/skill/config.

```
 HOST A (home)              HUB (public)              HOST B (work)
  sessions                 per-project               sessions
    | SendMessage          mailboxes (durable)         ^
  [ferry] <==== wss/tls ==> token auth + route <==== wss/tls ==> [ferry]
```

### ferry (per host)

- Publishes `remote:<project>` and `<host>:<project>` peers into the local
  session registry (they appear in `ListAgents`, take `SendMessage`). Proven
  mechanism (`tap.py` `Peer`).
- Watches `~/.claude/sessions/*.json`; maps each session cwd → git remote URL →
  project id. Announces projects it has (derived from active/recent session
  cwds, NOT a full-disk scan) to the hub.
- Holds one authenticated wss connection to the hub.
- Receive side: injects hub messages into a live local session as a local peer
  (the spike's proven path).
- All frame construction behind one adapter module, gated on registry
  `version`/`peerProtocol`; **fails closed** on drift.

### hub (one, public)

- Dumb authenticated store-and-forward. Per-project mailboxes, per-host bearer
  tokens, deliver-on-connect, hold-when-offline.
- No Claude, no session logic. Cannot originate a typed command — relay only.
- TLS only. Rejects unauth fast, rate-limits, caps message size at 1 MiB.
- Message TTL (~7 days default) + per-mailbox size cap.

## Addressing

- **`host_id`** per host (`home`, `work`, …), configured, bound to its token.
- Every envelope carries `origin_host` + origin `msg_id` (reply routing +
  dedup key).
- **`remote:<project>`** — fan-out to every OTHER host with that project.
- **`<host>:<project>`** — directed to one host (e.g. `work:iris`), the primary
  use (route heavy work to the unlimited-budget box).
- Ferry materializes per-host peers only for currently-online hosts;
  `remote:<project>` always present (the durable mailbox).
- Known semantic: `remote:` fan-out can produce multiple responders. Directed
  sends avoid it. A claim/lock message type is the future fix if needed — YAGNI
  for v1.

## Message types (v1)

Typed, whitelisted. Malformed → logged and dropped, never injected.

- `review_request` — review a PR/branch; reply with findings.
- `test_request` — run a suite/command; reply with results.
- `assign_issue` — delegate ownership of a GitHub issue to a host. Receiver
  side effect: `gh issue edit --add-assignee @me` + a comment on the issue
  (feeds the audit trail).
- `note` — freeform coordination.
- `reply` — response carrying `orig_msg_id`.

## Delivery

- **Peer live:** hub pushes → ferry selects a local session (prefer `bg`, else
  most-recently-active interactive) → rewrites `from` to a local
  `remote:<origin_host>` socket, preserves `hop-chain` verbatim → `SendMessage`.
  Reply routes back through the ferry to the hub to `origin_host`.
- **Peer offline:** hub holds in mailbox; drains when a ferry connects or
  reports a newly-live session for that project.
- **At-least-once + dedup:** hub holds until the ferry acks acceptance into a
  session; unacked messages redeliver on reconnect; ferry drops a repeat
  origin `msg_id` seen within a short window (default 10 min, configurable).
- **Pacing:** backlog drain respects the receiver's rate limiter (≤ ~1 msg/2s,
  no identical body within 30s).
- **hop-chain:** forwarded untouched, never trimmed. Ferry logs when a chain
  nears the `hop-loop` limit (~10 round-trips) — a genuine long dialog hitting
  the wall is a design conversation, not something to paper over.

## Auth & security

- Per-host bearer token over `wss://` (TLS). Token binds to one `host_id`;
  mismatch rejected. Stored 0600 in ferry config, NOT in `settings.json`.
- Hub is a relay, never an author: can replay/drop/reorder, cannot forge a
  typed command.
- Typed whitelist is the injection backstop: a hostile/garbage payload can't
  become an arbitrary prompt.
- Out of scope v1 (single trust domain): per-message signing, E2E encryption
  above TLS, per-user ACLs. Teammate support is the rewrite boundary; typed,
  host-scoped envelopes keep that future cheaper.
- Accepted risk: delivery is autonomous and after-the-fact, not gated — a bad
  `test_request` runs before the human notices. Bounded by the whitelist and
  relay-not-author properties.
- Unrelated but noted: the user's Discord bot token is plaintext in
  `~/.claude/settings.json`; rotate independently of this work.

## Audit

- Primary: native Claude Code rendering. Injected messages show as
  `Message from @remote:home (ctrl-o to expand)`; the response shows in the
  transcript / `timeline.jsonl` — identical to local peer messages. Nothing to
  build.
- Ground truth: ferry append-only log (in/out, origin, project, type, msg_id,
  delivery decision) — grown from `tap.log`, for debugging.
- Outward: per-type artifacts land where they belong (e.g. `assign_issue`
  comments on the issue).
- No hub dashboard in v1 (keeps hub dumb + small attack surface). A unified
  view later is a read-only tool tailing ferry logs, not a hub feature.

## Failure modes

- Hub down: ferry persists outbound queue, reconnects with backoff, drains.
  Local sends queue, don't fail.
- Receiving ferry down: hub holds mailbox, delivers on reconnect (normal case).
- Ferry crash: pid-owned registry entries reaped by other sessions'
  staleness check. Self-healing.
- Mailbox never drains: TTL + size cap.
- **Version drift (top technical risk):** unofficial unversioned
  `peerProtocol`; a `claude` update can change the frame format silently. Ferry
  gates on `version`/`peerProtocol`, isolates frame code behind one adapter,
  fails closed and alarms loudly rather than injecting garbage.

## Build order (each independently testable)

1. hub — mailbox + per-host token auth + wss (test with script client).
2. ferry send path — publish `remote:*` peers, forward to hub.
3. ferry receive/delivery — hub→session injection + target selection.
4. roster & addressing — `host_id`, `remote:` vs `<host>:`.
5. resilience — reconnect, store-and-forward drain, outbound persistence.
6. dedup + TTL.

Pure functions unit-tested: envelope schema, hop-chain passthrough, dedup,
cwd→git-remote→project-id mapping, version gating. Integration test: two
ferries + hub on localhost loop a `review_request`, assert delivery + reply —
a grown-up `tap.py` spike.

## Open questions (non-blocking)

- Hold behaviour under stricter permission modes (irrelevant while all sessions
  run auto).
- `peer_idle_notice` `detail` gating (cosmetic).
- Inbound peer-pid check when listener pid ≠ registry pid (only matters if the
  ferry ever forks its listener; design keeps listener in-process, so moot).
